# Цели и архитектура

## Исходная постановка

Пользователь работает из SQL и может вызвать модель через OpenAI-совместимый интерфейс. При первом знакомстве с базой полезно один раз собрать её структуру и получить обзор предметной области. Этот контекст нужен и разработчику, и генератору SQL-функций.

Начальная идея опиралась на [data2json/postresql-openai](https://github.com/data2json/postresql-openai). В этом проекте основной пользовательский интерфейс строится вокруг вызовов SQL-функций. Приоритет после каталога — `make_func` с двумя аргументами, именем функции и описанием. Генератор сам предлагает параметры и тип результата. Генерация представлений следует после функций.

Модель вызывается на этапе подготовки SQL. Применённый DDL создаёт обычную функцию или представление PostgreSQL, которое выполняется без модели. Служебный каталог позволяет повторно использовать результаты сканирования базы при следующем задании.

## Как устроен каталог

1. `ai.init_catalog` принимает имя схемы текущей базы, профиль модели и список разрешённых выборок. По умолчанию сканируется `public` и передаются только метаданные. Для нескольких схем функцию вызывают отдельно по каждой. Для другой базы подключаются к ней и запускают функцию там.
2. Функция читает каталоги PostgreSQL. Для таблиц и представлений она собирает имена и типы колонок, признак `NOT NULL`, комментарии, ограничения, валидные индексы и включённые пользовательские триггеры. Дополнительно сохраняются определения представлений, сигнатуры функций и агрегатов, описания доменов и перечислений.
3. Если указаны выборки, функция читает только перечисленные столбцы обычных и секционированных таблиц. Действуют лимиты до 8 таблиц, до 12 столбцов и от 1 до 5 строк на таблицу. При наличии первичного ключа первые строки выбираются по нему. Значения передаются как текст до 160 символов на поле. Такой срез показывает примеры значений и форматов.
4. `pgsql-http` отправляет каталог и выборки на `/v1/chat/completions`. Профиль задаёт полный URL, модель, таймаут и параметры запроса. При контексте свыше 250 000 байт функция завершает вызов с ошибкой. Модель получает задание описать на русском предметную область, смысл строк в таблицах, связи, типичные пути соединения и важные типы.
5. После успешного полного ответа функция вставляет или обновляет запись по уникальному `schema_name` и возвращает её `id`. При сетевой ошибке, HTTP-ошибке или оборванном ответе последний успешный результат остаётся доступен. При параллельных вызовах сканирование, начатое раньше, не перезаписывает уже сохранённый результат более позднего вызова.

| Объект | Содержимое |
| --- | --- |
| `ai.model_profile` | Профили OpenAI-совместимых моделей. `request_options` передаёт дополнительные параметры провайдера, например настройки Flash Next или `max_completion_tokens`. |
| `ai.catalog_snapshot.metadata` | JSON-каталог фактов, собранных из PostgreSQL. Ключ `schema` задаёт имя схемы. Массивы `relations`, `routines` и `types` можно читать и фильтровать из SQL. |
| `ai.catalog_snapshot.sample_manifest` | Таблицы и столбцы выборок, число прочитанных строк. Сырые строки уходят в запрос к модели и отдельно в снимке не сохраняются. |
| `ai.catalog_snapshot.synopsis` | Markdown-обзор модели для разработчика. Утверждения о типах, ограничениях и семантике стоит сверять с каталогом и SQL. |

В текущей установке доступ к схемам `ai` и `ai_http` закрыт для `PUBLIC`. Инициализация выполняется под владельцем или администратором. Отдельные роли для пользователей генератора и чтения каталога запланированы.

Прототип устанавливается SQL-скриптом. PostgreSQL использует расширение `http` как транспорт. Собственный пакет `CREATE EXTENSION` имеет смысл подготовить после стабилизации SQL-интерфейса и миграций служебных таблиц.

### Миграция прежнего каталога

`sql/install_catalog.sql` переводит прежний столбец `schemas text[]` в `schema_name text` и меняет сигнатуру `ai.init_catalog` с массива на имя схемы. Для дубликатов сохраняется запись с максимальным `captured_at`, при равенстве — с максимальным `id`. Повторный запуск установщика безопасен. Если в старом каталоге есть объединённый снимок нескольких схем, миграция останавливается с подсказкой, поскольку его обзор относится ко всем схемам сразу. Такой снимок можно экспортировать, удалить из каталога и после миграции инициализировать каждую схему отдельно.

### Что показал первый прогон

Обзор Flash Next предложил явно приводить типы для соединения `film_actor.film_id` с `film.film_id`. Обычный `JOIN` по равенству без приведения на демо-базе вернул 5 462 строки. В другом месте каталога `payment.rental_id` одновременно имеет `NOT NULL` и внешний ключ с `ON DELETE SET NULL`. Для генерации SQL полезно учитывать оба свойства. Из одного определения внешнего ключа нельзя вывести, что столбец допускает `NULL`.

## Генерация SQL-функций

Вызов на демо-базе:

```sql
SELECT * FROM ai.make_func(
    'reporting.customer_revenue',
    'По идентификатору клиента и периоду вернуть сумму его платежей.
     Начало периода включительно, конец исключительно.
     Если платежей нет, вернуть ноль.'
);
```

Пример сгенерированной сигнатуры:

```sql
reporting.customer_revenue(
    p_customer_id smallint,
    p_start_date timestamp without time zone,
    p_end_date timestamp without time zone
) RETURNS numeric
```

Генератор передаёт модели структурированные метаданные из сохранённых записей `ai.catalog_snapshot` в поле `catalog_snapshot`. Системный промпт указывает использовать этот снимок как источник имён, связей и типов. Целевая схема задаёт место создания функции. Источники данных могут быть в других схемах из снимка. Модель предлагает список аргументов и указывает исходный столбец для каждого. SQL-код берёт тип аргумента из этого столбца и проверяет его в PostgreSQL. В примере тип идентификатора берётся из `payment.customer_id`, а типы границ — из `payment.payment_date`. Тип результата модель предлагает по выражению `sum(amount)`.

В первой версии поддерживаются скалярные SQL-функции с одним `SELECT`. Для имени без схемы используется `public`. Генератор проверяет существование целевой схемы и право `CREATE`, собирает `CREATE FUNCTION` и выполняет его под правами вызывающего в той же транзакции. PostgreSQL проверяет тело и объявленный тип результата при создании. Повторное создание с той же сигнатурой возвращает ошибку. В результате вызова доступны сигнатура, выполненный DDL и допущения.

Созданная функция использует `SECURITY INVOKER` и обращается к данным без вызова модели. PostgreSQL проверяет корректность SQL, а соответствие результата бизнес-правилам проверяют на данных. На демо-базе `reporting.customer_revenue` сверяется с [эталонным запросом](../examples/customer_revenue_baseline.sql).
